必要になったところだけ引いてください。枠組みの全指標を採用する必要はありません。

運用で使う言葉

言葉意味と使い方
Goal / 目的誰のどんな状態を良くしたいか。
判断ログチーム単位で、決めたことと理由・日付・判断者を残す記録。様式は定めず、議事録・課題管理・表計算のどれに置くかはチームで決める。毎週書く項目と、一度決めて変わったときだけ書き直す項目がある（結論だけでなく、理由を残す）。
KGI / 成果指標目指す成果について期限までに達成する目標数値。本資料では指標名と目標値を分けて記入する。
制約今、成果を妨げている場所・条件。仕事の事実で確かめる。
CSF / 重要成功要因KGI達成のために、いま最優先で強化するプロセス。
KPI / 重点指標CSFの改善を確かめる指標と目標値。今週の行動を決め、KGI達成の見込みを確認する。
カウンターメトリクス（ガードレール指標）重点KPIの改善が品質・負荷などを悪化させていないか確かめる指標。本資料では許容する閾値と、超えたときの停止・再開条件を定めて運用する。
参照値四半期の全体確認に加え、制約の変化を調べる際にも使う数字。
個人評価に使わない原則指標をチーム・システムの改善に使い、個人のランキング・個人目標・人事評価点には使わないという本資料の運用方針。適用範囲を読む
ラグ / 時間差施策からKPI、KPIから成果へ変化が届くまでの時間。
PR / プルリクエストコードの変更をまとめてレビュー・統合を依頼する単位。
デプロイ変更を本番環境へ反映すること。日常の会話では検証環境への反映もデプロイと呼ぶが、本資料の指標が数えるのは本番環境への反映だけ。本番環境を持たない提供形態（モバイルアプリ、パッケージ、組込みなど）では、利用者へリリースした時点を代わりに数え、期を通じて同じ数え方に固定する。
WIP / 仕掛かり着手済みで未完了の仕事。
母集団指標を集計する対象に含める範囲。多くの指標では分母の抽出条件（どの記録を1件と数え、どれを除くか）に当たる。どのチームの・どの変更の記録を、どの期間で数えるかを先に決め、同じ指標を時期をまたいで比べるときは揃える。別のチームと並べる条件は別の話で、指標を個人単位に切り出す意味ではない（適用範囲を読む）。一部を抜き出して測るとき（サンプリング）は、抜き出した記録（標本）と母集団を分けて書く。

指標を個人の評価に使わない

本資料の指標・枠組みは、チーム・システムの改善を判断するためのものです。個人のランキング・個人目標・人事評価点に使うためのものではありません。これは本資料の運用方針です。指標の役割（重点KPI、カウンターメトリクス（ガードレール指標）、参照値）の違いも、雇用形態の違いも、この原則の適用を変えません。

使わない使い方意味
個人のランキング個人ごとに数値を並べた一覧・順位を作りません。会議資料、ダッシュボード、チーム横断の一覧を含みます。
個人目標指標や目標値を個人の目標欄へ転記しません。件数の目標として書き写すことも含みます。
人事評価点評価点へ換算しません。本採用・等級・昇給の判定根拠にしません。

この方針を置く理由は2つで、いずれも経験と構造から置いた仮説です（影響を確かめる4段階の「論理」に当たります。調査で検証した結果ではありません）。1つは、評価に直結すると報告の抑制・作業の分割・数字あわせが起きやすく、指標が改善の判断に使えなくなると考えるため。もう1つは、チームの数字には仕事の難易度、役割、他部署待ちなどが混ざるため、そこから個人の貢献を切り出すのが難しいためです。

個人は、合意した役割への貢献を成果物・協働・改善の事実で確認します。

本資料は同じ方針を開発生産性を捉える枠組みのDX Core 4の項にも書いています（本資料では、個人あたり活動量を人事評価点へ換算しません）。DX Core 4の原文が同旨を述べているかは、出典で確認してください。本資料の運用方針そのものは、外部の枠組みの記述に依存しません。

これは、人に関わることを測らない理由にはなりません。稼働の健全性や心理的安全性のように人に関わる指標も、測る対象はチーム・システムで、改善するのはチームの仕事と環境です。測るのをやめるのではなく、使い方と共有する単位を決めます。

個人単位の記録や式があること自体は、禁じていません

使わないと定めているのは上の3つの使い方です。記録や式が個人ごとになること自体は、次のように分けて扱います。この3つを混ぜると、指標ごとに厳しさが違うように読めます。

  • 個人単位で計測される：ツールや記録が利用者ごとに残ること。避けられない場合があり、禁じていません。共有する単位を下のとおり決めます。
  • 個人単位で算出される：式の値が個人ごとに決まること（入社日からの日数など）。指標によって違うため、個人ごとの値を作ってよいか、誰が見てよいか、どの単位で共有するかを、その指標のページとチームの判断ログで決めます。
  • 個人単位へ分解する：人数で割った集計値を1人ずつに割り戻すこと（例：エンジニア1人あたり指標の値を、1人ずつの成績として割り当てる）。比率としての意味が壊れ、数字だけを良くする行動を招くため、行いません。その指標自体は、組織の傾向を見るための集計値としては使えます。

共有する単位を決める

報告・一覧・比較（会議資料、ダッシュボード、期の集計、人の間で並べた表示）は、チーム以上の単位に固定します。少人数で個人が特定される粒度では出さず、上位の組織に合算するか、その期の公表を見送ります。人数の閾値について本資料は目安を置きません。チームで先に決め、週次の記録ではなく変更時だけ書き直す取り決めとして判断ログに残します（結論だけでなく、理由を残す）。

個人ごとの値を、本人と支援担当が支援のために見ることはできます。ただし次を先に決めて判断ログに残します。見る目的、見てよい人（評価の権限を持つ上長を含めません）、期の集計に残すもの（チームの代表値だけを残し、個別の値は残しません）。これも週次の記録ではなく、変更があったときだけ書き直す取り決めとして残します。所管・保存期間・閲覧できる範囲は人事・法務の定めに従い、判断ログにはその版と適用開始期を引用します。「支援のため」という説明だけで、見る人や残す範囲を広げません。これは指標の運用として残す集計の範囲の取り決めで、労働時間など法令や社内規程で保存が求められる記録の扱いを変えるものではありません。元の記録の保存期間と閲覧できる範囲は、人事・法務の定めに従います。

「個人」の範囲と、指標の母集団は別の話

ここでいう個人は雇用形態を問いません。派遣・業務委託の要員にも、上の3つの使い方をしない原則は同じように及びます。利用者ごとに値が残るツールでは、母集団に含めるかどうかと関係なく、自社の在籍記録に載らない要員の分も出ます。この値を契約の相手方（派遣元・委託先）との間でやり取りしません。相手方の手元で上の3つの使い方に回るためです。扱いに迷うときは、契約上の扱いを含めて人事・法務に確認します。

これとは別に、指標の分母に誰を含めるかは、指標ごとに決める事項です。対象に含める要員の区分を先に固定し、時系列で変えません。雇用形態の違う要員を含めるかは、契約上の扱いを含めて人事・法務に確認してから決めます。

責任者を置くことと、個人目標にすることは違う

KGI・KPIには対象・期限・責任者を決めます（第1章：成果を確かめるKGIを決める）。責任者は説明と是正の担当であり、達成度を個人の評価点へ換算する対象ではありません。成果の責任と、施策を実行する責任も分けて書きます（第1章：自部門が動かせる範囲を分ける）。

開発生産性を捉える枠組み

広木大地氏の開発生産性の整理を参考に、仕事量・狙った価値・実際に届いた価値を分けて話すと、経営と現場の議論を揃えられます。ここでの説明は要約と本資料の解釈です。どの枠組みも、指標を選ぶための材料として使います。

変更のリードタイム、デプロイ頻度、変更失敗率、デプロイ復旧時間、デプロイ手戻り率を、サービス単位で見ます。信頼性は別途監視します。

満足度・幸福感、成果、活動、コミュニケーションと協働、効率とフローを扱います。活動量だけに閉じないための枠組みです。

開発者体験と提供の状態、事業へのつながりをまとめて考える枠組みです。本資料では、個人あたり活動量を人事評価点へ換算しません（指標を個人の評価に使わない）。

DXの公式解説
EngThrive / 成果の指標と、原因を探る診断の指標を分けて持つ

Microsoftが自社の開発組織で運用する測定の体系です。速さ・容易さ・品質の3次元で、各次元の成果を示す指標と、原因を探る診断用の副指標を分けて持ち、テレメトリ（ツールが自動で記録する利用・稼働のデータ）と開発者への質問票調査を組み合わせます。開発者の状態（原典の語はThriving）が悪化していないかを併せて見る項目を、原典はガードレール（guardrail）と呼びます。本資料のカウンターメトリクス（ガードレール指標）が閾値と停止条件を持つ運用とは別の用法です。数字を良くしようとする行動が、そのまま実際の改善になる指標を選ぶ、という設計原則を掲げています。本資料では、原因を探る内訳は閾値を置かず参照値に当たり、閾値を置いて止めるカウンターメトリクスとは分けています。数字だけが良くなる行動は指標ごとに例示し、負担の移り先をカウンターメトリクスで見張る側に置いています。質問票はMicrosoft社内のもので、本資料はその調査票を提供せず、人に関わる指標もチーム単位で測り共有します（指標を個人の評価に使わない）。

EngThriveの論文（arXiv、2026年5月）

影響を確かめる4段階

強さ確かめ方気をつけること
実験対象を無作為に分け、条件を揃えて比較安全性・対象数・群間の影響を確認
準実験導入時期や近い条件の比較群を利用導入前の傾向や他の変化を確認
相関同時の変化、または対照のない前後比較別の原因を除けないことを明記
論理経験・構造から置いた仮説合意事項であり検証結果ではない

これは本資料の説明用の整理です。関係が弱い枝も消さず、次に何を確かめるかを記録します。測定対象、期間、比較群、他の要因を先に決め、後から都合のよい切り口だけを選びません。

すでにKPIマネジメントを運用している場合

Goal → KGI → プロセスの確認 → CSF → KPIという流れに、本資料の型・カタログを差し込めます。目的とKGIは第1章、プロセスとCSFは第2章、測定・合意は第3章、運用と見直しは第4・5章です。

中尾隆一郎氏は、Goal・KGI・CSF・KPIを関係づけ、最重要プロセスの目標数値をKPIと説明しています。著者による解説（2025年9月11日、Q1・Q2・Q4）を参照してください。本資料の章構成・開発組織の例・チームごとに1つとする運用・ガードレールの個数は独自の運用案です。著者が重視する組織全体の重点共有を踏まえ、チーム間の部分最適も確認します。原典の手順を置き換えるものではありません。出版社の書籍案内を参照してください。
