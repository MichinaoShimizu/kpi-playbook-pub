組織と働く環境

開発者体験指数

DX社のDeveloper Experience Index（DXI）は、開発者体験についてのサーベイを集約した指標です。任意の質問を合成した自社指数とは区別します。

DXI / Developer Experience Index

使い方の例：工程を改善する / KPI候補KGI・KPIの選び分け用語（KGI・CSF・KPI）

この指標に対応するプロセスが、いまのCSFである場合にKPI候補となります。KGIへのつながり、改善できる範囲、測定条件と目標値を合意してから採用します。

定義と測り方

開発者体験指数（DXI） = 利用するDX製品・定義の版に従う
自社サーベイによる独自指数 = 定めた質問・尺度・集約方法による値（DXIとは別物として記録する）

無記名のサーベイを、質問票・尺度・集約方法の版を固定して実施します（回答を識別するかどうかは、DX社（GetDX）の製品を使う場合は製品の設定と社内の合意で、自社サーベイの場合は社内の合意で、実施前に決めて記録します）。同社の製品を使う場合は製品の定義の版を、自社サーベイの場合（製品の質問・尺度・集約方法のどれか1つでも自社で入れ替えた場合を含む）は自社で定めた質問・尺度・集約方法を記録し、どちらかを明記します。集計単位はチーム以上とし、回答率と回答者の構成を併記します。未回答を良好とみなしません。記録から取れる摩擦（ビルド（プログラムの組み立て）や自動テスト（CI）の待ち時間、環境の不安定さ）は別に集め、サーベイの結果と突き合わせます。

率を使う指標は対象件数を併記し、分母ゼロは未定義、欠損は不明として扱います。期間・対象・除外条件・担当は、最初に一度、判断ログ（結論だけでなく、理由を残す）に残します（週次では書き直しません）。

図の下の箇条書きにある個人評価の断りは、本資料の運用方針で、就業規則・評価規程ではありません。図を持ち出すときはこの段落も併せて写してください（指標を個人の評価に使わない）。

この項目を使うとき

開発環境や情報へのアクセスの摩擦をサーベイで把握するとき。開発者向け調査の製品を提供するDX社（GetDX）の製品を使う場合はその定義の版に従い、自社サーベイで作る指数は別物として扱います。開発環境の摩擦（待ち時間、環境の不安定さ、情報の探しにくさ）を減らす工程を重点に置くときのKPI候補で、既存のログからは取れず、サーベイの実施が要ります。

採用する前に

指数の上昇を目標や評価に結び付けると、不満の出にくい時期を選んで実施する、質問を減らして高く出やすい構成にする、批判的な回答が多いチームを対象から外す、が起きやすくなります。質問・尺度・集約方法を変えたら別の指数として記録し、変更前後を連続した改善として並べません。少人数の集団は単独で出さず、上位の組織に合算します。

KPIの基準値と目標を合意する

目標の置き方と基準値

KPIに置くなら、対象（チーム・部門）と質問票の版を固定し、同じ版で2回以上の調査から基準値を取り、目標は同じ版の指数か、基準値を取った時点で最も低かった構成項目（期をまたいで固定する）の得点で、指数の単位（尺度の点）で書きます（記入例：最も低い構成項目の得点を基準値から5ポイント改善。数値は架空で、尺度は質問票の版に従います。構成項目の例は、自社サーベイならビルドの待ち時間や環境の構築のしやすさ、DX社の製品なら製品が定義する項目）。

目標欄に書かないもの

記録から取れる待ち時間・手戻り率は対の候補として別に置き、目標欄には書きません。回答率の下限を合意し、下回った期は判定しません。この指数を個人の目標欄に転記せず、評価点にも換算しません。

調査が2回に満たない期

同じ版の結果が2回に満たない期は、目標値を置かず基準値を取る期として提出し、目標値は2回目以降の期に置きます。

カウンターメトリクス（ガードレール指標）

対にする指標の考え方と、閾値の決め方・超えたときに止めるもの

対に置くのは、この指標の数字を良くしようとする行動が、品質・負荷・費用に出す副作用を捉える指標です。数字は、仕事の中身を良くしなくても、負担を別の場所へ移すことで動きます。移した先はこの指標には表れません。下の候補は、その移り先（品質、人の負荷、費用、測り方、顧客）を先に決めて見張るためのものです。この移り先の整理は本資料の運用案で、調査で得た知見ではありません。どこへ移るかはチームが実際に採る行動で変わるため、写す前に自チームの行動から選び直してください（なぜ、その指標が対になるのか）。

対に置く指標は達成目標ではなく、超えたら止める閾値として使います。何から決まる閾値かを先に決めてください。法令・労使協定・社内規程で上限が決まっている項目と、顧客が必要とする水準や予算・資金の制約から決まる項目は、自社の分布からではなく、その上限・要求・制約を根拠にし、上限に達する前に手を打てる水準に置きます（上限そのものを閾値にしません）。自社の分布から決める項目は、基準値とばらつきから置きます（閾値の決め方と停止・再開条件）。

超えたときに止める対象、再開を判断する人、再判定の時期をチームで決め、判断ログ（結論だけでなく、理由を残す）に残します。止めるのは閾値に触れさせた施策や進め方で、保守・セキュリティ更新のような投資の区分を止めることではありません。

  • 調査の回答率・回答者構成
  • 測定定義の変更回数
  • 記録から取れる待ち時間・手戻り率
  • 稼働の健全性

上の候補からチームで2〜4個を選び、達成目標ではなく超えたら止める閾値として置きます（個数は本資料の運用方針）。対に置くのは、この指標の数字を良くしようとする行動が品質・人の負荷・費用・顧客へ出す副作用と、数え方の変更を捉える指標です。法令・労使協定・社内規程の上限、顧客の要求、予算の制約から決まる項目は、先にそれを確かめます。選ばなかった項目は四半期の確認に回し、観点だけが並ぶ場合は自チームで閾値を置ける指標に具体化してから使います。止めるのは閾値に触れさせた施策や進め方で、止める対象・再開を判断する人・再判定の時期を判断ログ（結論だけでなく、理由を残す）に残します。

リンクは、本資料に同じ名前のページがある項目にだけ付いています。近い名前のページは指標カタログで探せます。

質問数や集約方法を独自に変えた値をDXIと呼んだり、DXのベンチマークと直接比較したりしません。本資料は質問票や採点ロジックを提供していません。

打ち手と確かめ方

低い項目について、記録から取れる量（待ち時間、ビルドやCIの失敗の割合）と自由記述で原因を確かめ、開発環境・ツール・情報の置き場所の改善を1つずつ試します。回答を促す働きかけで値を作りません。

指数が上がった期に、質問票の版・回答率・回答者の構成が前回と同じか、記録から取れる待ち時間や手戻り率が同じ向きに改善しているかを確認します。稼働の健全性が悪化していないかも見ます。環境改善の後は、合意した時期（例：次回の定期調査）で再確認します。
